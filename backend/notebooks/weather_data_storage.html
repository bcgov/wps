Weather data storage¶

We have been moving weather data out of the Postgres database and into files on object storage. The database got too big to keep much history, so older model data was archived and removed every month. Object storage is cheap enough that we can keep it.

There are two parts to the work. The first is weather at stations: observations, forecasters' forecasts and model values. The second is new. We now also store the model forecasts as maps covering all of BC, so a forecast can be looked up at any location and not only at a station.

Everything described here is running in our development environment. Production has not been moved yet.

The Station Weather API is how other teams can get the station data. They need a key. The maps are not in the API yet.

Accuracy¶

The forecast centres round their values before they publish them. We store the published numbers without rounding them again, so what we read back is what they published.

Some services, such as Open-Meteo, do round a second time to save space. Money is a reasonable comparison. If a price works out to 23.4567 dollars, the shop rounds it to 23.46, and we keep the 23.46. Rounding again is like only having nickels, where 23.46 becomes 23.45. So do 23.43 and 23.47, and afterwards there is no way to tell them apart.

How long we keep the maps, and the cost¶

Each run of a model covers much of the same period as the one before, so keeping every run would mostly be storing the same days over again. We keep every run for 48 hours. After that we keep one run a day, the last full-length one, and delete the others.

For example, HRDPS runs four times a day. At the end of a Saturday we would have all four runs from Friday and from Saturday, and one run for every day before that.

This comes to about 52 GB a year for the five models. Keeping every run would be about 200 GB a year. Keeping one original file set a day, instead of cutting out BC, would be about 1 TB.

At 7 cents per GB per month, each year of maps costs about 44 dollars a year to keep. Deleted maps stay on the storage for another 60 days, and I estimate that would add about 27 dollars a year if we are billed for it.

Failures¶

  • If a job is stopped part way through, the next one continues from where it stopped, without storing anything twice.
  • If a forecast centre is slow or unavailable, runs that were already downloaded are still published and the missing ones are tried again.
  • A map run is only stored once all of it has been published.
  • Each model has two map stores, one for the last 48 hours and one permanent. On November 23 the 48-hour store for HRDPS stopped accepting data for about 12 hours, and that held up the permanent one too. They are now independent. We don't know yet why it stopped.

Station data can be read as it was at any point in the last 30 days, which helps if something is changed by mistake. For the maps it is about one day.

Appendix: how a value is stored¶

The forecast centres publish each value in a packed form, and we store the same numbers they do:

$$\text{value} = \frac{R + X \cdot 2^E}{10^D}$$

$X$ is a whole number stored for every grid cell. $R$, $E$ and $D$ are stored once per forecast hour. The table shows the price from the accuracy section written this way, and one cell of the forecast above, in kelvin.
